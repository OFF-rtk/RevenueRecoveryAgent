# Revenue Recovery Agent - Judge Dashboard Frontend Structure

This document outlines the page-by-page structure for the Judge Dashboard & Sandbox, mapped exactly to the data our Postgres database and backend can provide. Hand this off to the agent building the UI in the `tricerolabs` repository.

## Global Layout
- **Sidebar/Nav:** Fixed left navigation with 3 tabs: Dashboard, Case Explorer, Live Interaction.
- **Theme:** Inherit the existing `tricerolabs.com` design system (Tailwind classes, fonts, dark/light mode).
- **Routing:** Assume base route is `/revrecagent` with sub-routes `/dashboard`, `/explorer`, `/sandbox`.

---

## 1. Dashboard (Batch Summary)
**Path:** `/revrecagent` or `/revrecagent/dashboard`
**Purpose:** High-level metrics proving the track's bar (recovery rate, accuracy, financial impact).

### UI Structure
*   **Header:** Title "Batch Summary" + static "Batch ID: BT-24X9A" badge.
*   **Top Metrics Grid (4 Cards):**
    1.  Total Cases Processed
    2.  Overall Recovery Rate
    3.  Total Recovered (₹)
    4.  Total At Risk (Pending ₹)
*   **Evidence Sources (2 Columns):**
    1.  *Ground Truth Local Batch:* Shows Diagnosis Accuracy, False Positive Rate, and Total Volume Processed.
    2.  *Live LLM-Persona Batch:* Shows Simulated Recovery Rate, Avg Interaction Turns.
*   **Per-Persona Recovery Table:**
    *   Columns: Persona Profile | Attempted | Recovered | Success Rate
    *   Rows: Compliant/Low Resistance, Skeptical/Medium Resistance, Hostile/High Resistance.

### Backend Mapping (To Be Built)
*   `GET /api/dashboard/summary`: Will aggregate `cases` (count, status percentages), `outcomes` (amount_recovered sum), and `diagnoses` (is_correct boolean).
*   `GET /api/dashboard/persona-breakdown`: Will aggregate outcomes filtering by cases tagged as generated by specific personas in the harness.

## 2. Case Explorer
**Path:** `/revrecagent/explorer`
**Purpose:** Browse historical cases and view their explicit audit trails.

### UI Structure
*   **Filters Bar:** Dropdowns for Status (recovered, escalated, etc.), Case Type, and Diagnosis Tier (1 or 2).
*   **Cases Table:**
    *   Columns: Case ID | Amount | Root Cause (Diagnosis) | Final Status | Last Updated
*   **Case Detail Drawer/Modal:**
    *   When a row is clicked, slide out a panel showing the chronological **Audit Trail**.
    *   Needs custom visual flags for specific event types:
        *   🔴 **Stopping Rules** (e.g., max-retry hit, opt-out).
        *   🟡 **Escalations** (retry-exhausted vs disputed vs missing human data).
        *   🔵 **Manual Triggers** (cron stand-ins).

### Backend Mapping (To Be Built)
*   `GET /api/cases?status=X&type=Y&tier=Z`: Queries `cases` joined with `diagnoses`.
*   `GET /api/cases/:id/timeline`: Unified chronological feed aggregating:
    *   `audit_events` (for system actions/triggers)
    *   `state_transitions` (for state machine changes)
    *   `interventions` (for agent messages)
    *   `replies` (for customer messages)

## 3. Live Interaction (Sandbox)
**Path:** `/revrecagent/sandbox`
**Purpose:** Interactive proof that the system works in real-time, using real production code paths.

### UI Structure
*   **Left Panel (Case Initiator):**
    *   Dropdowns: Case Type, Root Cause.
    *   Button: "Trigger Case" (Spawns the case).
*   **Center Panel (Chat Canvas):**
    *   Header: "Simulated Customer (ID: ...)"
    *   Canvas: Renders Left/Right chat bubbles (Agent on Right, Customer on Left). System messages in center pill-boxes.
    *   Reply Controls (Bottom):
        *   Textarea for free-text manual replies.
        *   Dropdown to select an LLM Persona (Confused, Aggressive, etc.).
        *   Button: "Send" (Manual) or "Run Persona".
*   **Right Panel (Live Audit Trail):**
    *   Real-time vertical timeline exactly like the Case Explorer detail view, but updates live as the chat progresses.
    *   Bottom Button: "Check Follow-ups Now" (Manual cron trigger).

### Backend Mapping (To Be Built)
*   `POST /api/sandbox/trigger`: Takes `{ case_type, cause }`. Fires a synthetic Razorpay webhook to our endpoint. Returns `{ case_id }`.
*   `GET /api/cases/:id/chat`: Polls `interventions` and `replies` to render the bubbles.
*   `GET /api/cases/:id/audit`: Polls `audit_events` to render the right timeline panel.
*   `POST /api/sandbox/reply/manual`: Takes `{ case_id, text }`. Fires an inbound WhatsApp webhook to simulate the customer texting back.
*   `POST /api/sandbox/reply/persona`: Takes `{ case_id, persona_type }`. Runs the `call_llm` persona function on the backend, gets the text, and fires the inbound WhatsApp webhook.
*   `POST /api/sandbox/force-cron`: Takes `{ case_id }`. Manually executes `check_stopping_rules` and follow-up logic to skip waiting times.
