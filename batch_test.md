# Live Persona Batch Test — Methodology & Results

This document is the full record of the 50-case live persona simulation referenced in the README and pitch video: how it's run, what it's actually testing, and the complete results, aggregate and per-persona. The harness itself is `scripts/run_live_persona_harness.py`.

---

## 1. What this test actually is

Most "eval" numbers in a demo are either hand-picked or generated by a script whose ending is already decided. This harness is built specifically to avoid that: it runs the real, deployed recovery pipeline — the same FastAPI backend, database, diagnosis LLM, and WhatsApp-webhook state machine used in production — against a **second, independent LLM** whose only job is to improvise as a customer. Neither model is told how the conversation should end. The outcome of each case is whatever the two systems actually produce when they talk to each other.

Concretely:
- **The agent under test** is hit over real HTTP, exactly like a real Razorpay/Meta webhook would hit it — `POST /webhooks/razorpay` (`payment.failed`) to create a case, `POST /webhooks/whatsapp` to simulate an inbound customer reply, `POST /webhooks/razorpay` (`payment.captured`) if the persona decides to pay.
- **The customer** is played by Cerebras-hosted `gpt-oss-120b`, given a persona description and nothing else — no script, no expected ending, just a "tendency" (see §3).
- Everything runs against `BASE_URL=https://revenuerecoveryagent.onrender.com` by default — the live deployed instance, not a local dev server.

## 2. Configuration

| Setting | Value |
|---|---|
| Backend under test | Live deployed instance (`revenuerecoveryagent.onrender.com`) |
| Persona LLM | Cerebras `gpt-oss-120b` |
| Persona temperature | Randomized per case, uniform between **0.7 and 0.9** — so identical personas don't produce identical conversations |
| Max conversation rounds | 40 (a round = one poll of the case's DB state, ~10s apart) |
| Max replies per case | 10 (12 for `considering_cancellation`, since ambivalence-driven conversations tend to run longer) |
| Case count (this run) | 50 |
| Customer identity | Synthetic phone numbers (`919000...` prefix), each one a distinct `Case` row in the real database |
| Outbound channel | Real `WhatsAppChannel` code path — sends genuinely fail with Meta's `(#131030) recipient not in allowed list)` for these synthetic numbers, which is expected and doesn't block the pipeline (the state machine only depends on what's written to the database, not on whether the WhatsApp send itself succeeded) |
| Inbound channel | The harness posts directly to `/webhooks/whatsapp` with a valid HMAC signature, exactly matching what Meta's real webhook payload shape looks like |

Between rounds, if a case has no new agent message to react to, the harness has a 50% chance of forcing a follow-up check (`check_followup(..., force=True, use_mock=True)`) to advance stale cases rather than waiting out the real proactive-scheduler interval.

## 3. The six personas

Each persona is given a *tendency*, explicitly not a scripted outcome — the system prompt tells the persona LLM: *"Your tendencies below describe how you LEAN, not a script you must follow... Do not treat your outcome as predetermined by your persona alone."*

1. **`accidental_failure`** — A happy customer whose payment failed by accident. No underlying reason to refuse; leans toward paying quickly once the issue is explained clearly.
2. **`suspicious_payer`** — Doesn't recognize the charge or product name. Will ask at least one clarifying question before doing anything. Becomes *more* suspicious, not less, if the agent's answer is vague or doesn't actually address the question.
3. **`needs_payment_help`** — Willing to pay, but the failure is a real card/payment-method problem. Needs the agent to actually offer a fix (e.g. UPI) rather than repeat "please pay" — and even once offered a working option, doesn't treat it as an automatic done deal in the same exchange.
4. **`considering_cancellation`** — Genuinely on the fence about keeping the subscription at all. The payment failure is a natural moment to reconsider, not just an accident to fix.
5. **`ignores_completely`** — Never responds, under any circumstances. Tests the no-reply → escalation/timeout path.
6. **`forgetful_promises_then_pays`** — Willing to pay, but busy and forgetful. Almost always promises to pay later on first contact rather than paying immediately; more likely (not guaranteed) to actually pay once a real follow-up reminder arrives.

## 4. The six failure scenarios

Each case is assigned a random real Razorpay failure mode. This isn't cosmetic — `error_description`, `product_description`, and `payment_method` all flow directly into both the diagnosis prompt and the reply-drafting prompt, so varying them changes what the agent actually has to reason about and respond to.

| Product | Amount | Method | Failure reason |
|---|---|---|---|
| Razorpay Premium Annual Subscription | ₹999 | Card | Insufficient funds |
| Razorpay Pro Monthly Plan | ₹499 | Card | Card expired |
| Razorpay Business Suite Subscription | ₹2,999 | Card | Incorrect CVV |
| Razorpay Premium Annual Subscription | ₹999 | Card | Declined by issuing bank |
| Razorpay Team Plan Subscription | ₹1,499 | UPI | UPI Autopay mandate revoked by customer |
| Razorpay Pro Monthly Plan | ₹499 | Card | Temporary gateway timeout |

## 6. Results — aggregate (50 cases)

| Outcome | Count | Rate |
|---|---|---|
| Recovered (paid) | 22 | 44.0% |
| Retained via pause | 12 | 24.0% |
| Escalated to human | 7 | 14.0% |
| Timed out (no resolution) | 9 | 18.0% |
| Stopped (opt-out) | 0 | 0.0% |
| Error | 0 | 0.0% |

**KPIs:**
- Recovery rate: **44.0%**
- Retention rate (recovered + retained on a paused plan, i.e. "kept the customer in some form"): **68.0%**

## 7. Results — per persona

| Persona | Cases | Recovered | Retained (paused) | Escalated | Timeout |
|---|---|---|---|---|---|
| `accidental_failure` | 8 | **100.0%** | 0.0% | 0.0% | 0.0% |
| `needs_payment_help` | 10 | **100.0%** | 0.0% | 0.0% | 0.0% |
| `forgetful_promises_then_pays` | 7 | 57.1% | 0.0% | 0.0% | 42.9% |
| `considering_cancellation` | 13 | 0.0% | **92.3%** | 7.7% | 0.0% |
| `suspicious_payer` | 6 | **0.0%** | 0.0% | **100.0%** | 0.0% |
| `ignores_completely` | 6 | 0.0% | 0.0% | 0.0% | **100.0%** |

### Reading these numbers honestly

- **`accidental_failure` and `needs_payment_help` converting at 100%** is expected, not impressive on its own — neither persona has any underlying reason to refuse once the issue is competently handled. They're the floor, not the headline.
- **`considering_cancellation` resolving to a 92.3% retained-pause rate, not lost customers**, reflects a deliberate choice in the negotiation prompt: ambivalence doesn't collapse into an immediate concession. The agent offers a pause and surfaces real value first, and only fully disengages if the customer explicitly and unambiguously opts out.
- **`suspicious_payer` converting at 0% is the most important number in this table, not a weak spot.** This persona asks for account details (signup dates, receipts) the agent genuinely doesn't have access to. Every one of its 6 cases ends in a correct human escalation — the agent declines to fabricate an answer rather than hallucinating something plausible-sounding to close the case. A system that never says "I don't know" isn't trustworthy; 0% recovery here is the agent proving it knows the limits of its own authority.
- **`ignores_completely` timing out at 100%** is the intended behavior for a customer who never engages at all — there's no reply to escalate on, so the case exhausts its retry cap and times out rather than being marked as a false "escalation."

## 8. Caveats

- This run bypasses the real Meta WhatsApp Cloud API by design — synthetic `919000...` numbers were never added to Meta's sandbox allow-list, so any *real* WhatsApp send against them fails with `(#131030)`. This is expected and doesn't affect the result: the state machine, diagnosis, and stopping rules all operate on what's written to the database, not on whether the outbound WhatsApp API call itself succeeded. Inbound replies are simulated by posting directly to the app's own webhook endpoint with a valid signature, exactly matching the shape of a real Meta payload.
- Outcomes are **not reproducible run-to-run** by design — persona temperature is randomized (0.7–0.9) and personas are explicitly instructed not to treat their outcome as predetermined. This is intentional: the point of this harness is that the numbers are an emergent result of a real conversation, not a fixed script.
- Raw per-case data (every persona's `internal_reasoning`, full conversation summaries, and round-by-round state) is saved to `data/live_persona_state.json` during the run and the full structured report to `reports/live_persona_report.json` — both are the actual source data these tables are generated from.
